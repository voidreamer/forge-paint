SUMMARY
-------
The 3Delight Hydra render delegate (HdNSIRendererPlugin) rendered fine in
forge-paint on macOS but failed on Windows: the out-of-process startup probe
exited with code 3 and the viewport fell back to Storm-only.

Root cause was a platform graphics-API difference. hdNSI requires a GPU
graphics device (an Hgi) to load; macOS provides one headlessly (Metal) for
free, Windows (OpenGL) does not. FIX: the bridge now creates a hidden
window + WGL context on Windows so it can take the exact same
gpuEnabled=true HGI path macOS uses. Verified on this box: the probe now
exits 0 for both HdNSIRendererPlugin and HdStormRendererPlugin.

ROOT CAUSE (unchanged analysis, now confirmed)
----------------------------------------------
1. forge-paint's Hydra bridge (rust-usd/hydra-rs/cpp/hydra_bridge.cpp,
   create_renderer) builds a pxr::UsdImagingGLEngine to drive Hydra.

2. On Windows it used to take a "no-HGI" path:
       UsdImagingGLEngine(HdDriver(), "HdNSIRendererPlugin", gpuEnabled=false)
   (added to dodge a Windows hang during Hgi creation).

3. UsdImagingGLEngine::SetRendererPlugin gates loading an explicit delegate
   on plugin->IsSupported(_gpuEnabled). With gpuEnabled=false, hdNSI's
   IsSupported(false) returns FALSE. The gate fails, no delegate loads, no
   color AOV buffer exists, the probe throws and exits 3.

4. The Hgi-creation hang the old dodge avoided: on Windows the platform-
   default Hgi is HgiGL, and HgiGL does not create a GL device — it adopts
   whatever GL context is current on the calling thread and touches driver
   entry points immediately. Headless processes (the probe; forge-paint
   itself renders via wgpu) never have one, so creation died in driver
   code. macOS never hits this: HgiMetal creates its own headless device.


THE FIX (implemented in hydra-rs 0.0.11)
----------------------------------------
Give Windows what macOS gets for free: a real but invisible GPU context.

hydra_bridge.cpp now creates, once per process, a never-shown window and a
WGL context (wglCreateContextAttribsARB, 4.5 COMPATIBILITY profile, legacy
wglCreateContext fallback), makes it current on the calling thread, and
then takes the same gpuEnabled=true / CreatePlatformDefaultHgi path macOS
uses. hdNSI passes the IsSupported(true) gate, loads, and renders on the
CPU; the GL context only exists so HgiGL can be constructed (presentation
stays disabled). The context's currency is re-asserted in render_color(),
set_renderer_plugin(), and ~Renderer() (HgiGL teardown also makes GL
calls). If no usable >= 4.5 GL context can be created (remote desktop,
no driver), the bridge falls back to the old no-HGI route and leaves a
breadcrumb naming why.

Two details that cost a debugging round each, recorded for posterity:

* COMPATIBILITY profile is load-bearing. A 4.5 CORE context lets the
  delegate load but every draw errors out (empty image): HgiGL's
  ScopedStateHolder saves/restores GL_POINT_SMOOTH / GL_POINT_SPRITE,
  which are removed from core (GL_INVALID_ENUM), and Storm's indirect
  draws fail on strict core. Everything USD normally runs on (usdview's
  Qt contexts, GarchGLDebugWindow) is compatibility profile.

* C getenv vs Rust set_var: the bridge's breadcrumbs gate on
  getenv("FORGE_PAINT_HYDRA_LOG"). The Windows CRT snapshots the
  environment at process start, so std::env::set_var from Rust inside the
  same process is invisible to the C++ side. Breadcrumbs appear when the
  env var is set in the PARENT (the app sets it on the probe child via
  Command::env; for manual runs, set it in the shell first).

Build-side changes: hydra-rs/build.rs links user32 + gdi32 + opengl32 on
Windows targets. hydra-rs version 0.0.10 -> 0.0.11; forge-paint pins
hydra-rs = "0.0.11".

LOCAL END-TO-END TEST RECIPE (Windows box)
------------------------------------------
The old "local hdNSI testing is unreliable" caveat is gone: build hdNSI
from source against the local USD and the whole stack runs locally.

Build forge-paint against local USD 25.11 (python-enabled):
  $env:USD_INSTALL_DIR = "C:\Users\voidr\usd"
  $env:USD_LIB_PREFIX = "usd_"
  $env:USD_LINK_PYTHON = "lib"
  $env:USD_PYTHON_INCLUDE_DIR = "$env:LOCALAPPDATA\Programs\Python\Python313\include"
  $env:USD_PYTHON_LIB_DIR = "$env:LOCALAPPDATA\Programs\Python\Python313\libs"
  $env:USD_PYTHON_LIB_NAME = "python313"
  $env:CXXFLAGS = "/std:c++17 /Zc:__cplusplus /EHsc /DNOMINMAX /DWIN32_LEAN_AND_MEAN /D_USE_MATH_DEFINES"
  cargo build --release        # [patch.crates-io] uses ../rust-usd sources

Build hdNSI against the same USD (one-time, reusable):
  git clone --depth 1 https://gitlab.com/3Delight/HydraNSI.git <src>
  cmake -S <src> -B <build> -G "Visual Studio 17 2022" -A x64 `
    -Dpxr_DIR="C:\Users\voidr\usd" -DCMAKE_PREFIX_PATH="C:\Users\voidr\usd" `
    -DOpenSubdiv_ROOT="C:\Users\voidr\usd"
  cmake --build <build> --config Release --parallel
  cmake --install <build> --config Release --prefix <install>
  # PXR_PLUGINPATH_NAME entry: <install>\hdNSI\resources

Run the probe:
  $env:PATH = "C:\Users\voidr\usd\lib;C:\Users\voidr\usd\bin;" +
              "$env:LOCALAPPDATA\Programs\Python\Python313;" +
              "C:\Program Files\3Delight\bin;$env:PATH"
  $env:DELIGHT = "C:\Program Files\3Delight"
  $env:PXR_PLUGINPATH_NAME = "<install>\hdNSI\resources"
  $env:FORGE_PAINT_HYDRA_LOG = "$env:TEMP\hydra_bridge_probe.log"  # breadcrumbs
  $env:FORGE_PAINT_HYDRA_PROBE = "1"
  $env:FORGE_PAINT_HYDRA_PROBE_STAGE = "<repo>\assets\default_mesh\default.usda"
  $env:FORGE_PAINT_HYDRA_PROBE_DELEGATE = "HdNSIRendererPlugin"
  target\release\forge-paint.exe        # exit 0 = pass, 3 = fail

(The locally-built exe links USD 25.11, so the 25.05-built hdNSI bundled in

CI ARTIFACT FOLLOW-UP (2026-06-09, evening)
===========================================
hydra-rs 0.0.11 published 19:14Z; windows-build run 27229782417 built
from f58fa5d with include_hdnsi=true and succeeded. The artifact zip
(forge-paint-windows-0.0.11) still failed on this box: no Storm in the
picker, and switching to 3Delight reported it couldn't be found. The
bridge fix is PRESENT and working in the artifact ("wgl: hidden GL
context ready" appears in the probe trail). Three separate
forge-paint-side bugs were stacked on top of it:

1. OpenUSD DOUBLE-LOAD -> Hgi::CreatePlatformDefaultHgi deadlock.
   The zip keeps copies of the USD runtime DLLs beside the EXE so the
   import table resolves for direct launches. USD's plug registry later
   LoadLibrary()s the SAME libraries by absolute path from usd\lib\
   (plugInfo LibraryPath entries). The Windows loader dedupes modules
   by path, not name, so every USD module existed twice in the process;
   the first Hydra bring-up then hung forever inside
   Hgi::CreatePlatformDefaultHgi (probe timeout after 15 s — the
   "[hydra-bridge] create_renderer: Hgi::CreatePlatformDefaultHgi" line
   with nothing after it). The same line returns "Hgi OK (OpenGL)"
   locally because dev runs load USD from one place (PATH), never two.

2. ENV CAPTURED BEFORE main() -> empty plug registry on direct launch.
   pxr/base/plug/initConfig.cpp registers plugin search paths in
   ARCH_CONSTRUCTOR(Plug_InitConfig, 2), which runs while usd_plug.dll
   loads — before main(). std::env::set_var in setup_bundled_usd_env
   was therefore invisible to plugin discovery (and C-runtime getenv —
   DELIGHT, FORGE_PAINT_HYDRA_LOG — snapshots at process start, same
   problem). Only forge-paint.bat launches worked, because the .bat
   sets the variables in the shell. This is why a double-clicked
   artifact logged "Hydra render delegate not registered: ...
   Available: []" and "UsdStage::Open returned null" (19:43 / 19:50
   sessions in the artifact's forge-paint.log).

3. hdNSI STAGED FROM THE BUILD TREE, NOT THE INSTALL.
   package-hdnsi-windows.ps1 grabbed the first plugInfo.json under the
   CMake BUILD dir (<build>\hdNSI\plugInfo.json, the configured copy
   that the INSTALL step would place into hdNSI\resources\). Staged at
   plugins\usd\hdNSI\plugInfo.json, its Root ".." + LibraryPath
   "hdNSI.dll" resolved to plugins\usd\hdNSI.dll — nonexistent; the
   real DLL sat in plugins\usd\hdNSI\Release\. USD registered the
   delegate from the metadata (so "3Delight" appeared in the picker)
   but loading failed:
     Failed to load plugin 'hdNSI': The specified module could not be
     found. in '...plugins/usd/hdNSI.dll'
   That error is the user-visible "cannot find 3Delight".

FIXES (this commit, all in forge-paint)
---------------------------------------
* src/main.rs: relaunch_from_bundled_usd_lib() — bundle-root EXE
  computes the bundle env and relaunches the new usd\lib\forge-paint.exe
  copy with it, then forwards the exit code. Child imports resolve from
  usd\lib (same files plug loads -> single instance, fixes 1) and the
  env exists at process start (fixes 2, including CRT getenv readers:
  the parent also passes FORGE_PAINT_HYDRA_LOG so bridge breadcrumbs
  now work in the app process, and FORGE_PAINT_LOG_FILE keeps the log
  beside the root EXE). setup_bundled_usd_env stays as the macOS path
  and the fallback for old zips.
* .github/workflows/windows-build.yml: stages the usd\lib EXE copy;
  hard-fails unless hdnsi-package has hdNSI\hdNSI.dll +
  hdNSI\resources\plugInfo.json; README text updated.
* .github/scripts/package-hdnsi-windows.ps1: runs cmake --install and
  stages the installed prefix (hdNSI + usdNSI when present); validates
  the layout; strips *.lib/*.pdb (fixes 3).
* src/hydra_view.rs: Storm visible by default on Windows
  (FORGE_PAINT_ENABLE_STORM=0 hides it — checklist item 5 from the
  previous section, now that the probe matrix above confirms the CI
  artifact).
* src/app.rs: the out-of-process startup probe now guards EVERY Hydra
  delegate on Windows (Storm included), with delegate-aware overlay
  text; protects the no-GL-context cases (remote desktop, missing
  driver) that the WGL fix cannot cover.
